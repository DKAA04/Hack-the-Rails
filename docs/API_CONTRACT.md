# Wayward API contract v1

Canonical source: packages/contracts/src. All consumers import @wayward/contracts. Version 1 uses camelCase JSON and UTC ISO timestamps ending in Z, plus IANA time zones on places. Money is a nonnegative safe integer in minor units and an uppercase ISO currency code. No floating-point currency calculations. Provider IDs are opaque strings; do not parse or replace them with display names.

SearchIntent includes resolved typed places, passenger ages and discount references, dates, bag counts, modes, preferences and optional natural-language text. Natural language is input, not an implemented inference service. Place resolution must be integrated before frontend submission; raw labels must not masquerade as resolved supplier IDs.

Transport modes: flight, rail, coach, ferry, local_transit, walking, transfer. Itineraries distinguish completeness and verified compatibility; leg timing alone does not prove a valid or protected connection. Transfers record minimum buffers, location changes, protection and compatibility. Supplier capability mode lists indicate intended adapter scope, not confirmed commercial coverage.

Price.kind explicitly separates live_offer, test_offer, indicative, historical_observation, published_tariff_range and unknown. Known totals identify complete/partial status, missing components and priced components. Complete totals must include all mandatory fare, tax, service, bag, transfer and payment costs, in one currency; no silent FX conversion. Unknown prices have no numeric total. Tariff ranges are not offers. Nullable fields mean unknown, never zero or false by implication. Services absent from includedServices remain unknown. Availability and reservationState are independent of timetableStatus, crowding and seatMapAvailable. No held seat or issued ticket can be inferred from a timetable.

Offers carry seller/merchant identity, conditions, included services, provider references, freshness and expiry, availability and live/test environment. Revalidation must verify expiry, availability, complete total and customer acceptance of changes before order creation. Only live or explicitly test-environment supplier offers can reach an appropriately matching purchase environment. The skeleton does not implement those transitions.

Parent Order owns supplier child bookings. Customer payment state, supplier settlement state and fulfillment state are independent. TicketDocument requires actual supplier issuance. Aftersales refund/exchange/cancellation capabilities are explicit supported/unsupported/unknown; no capability is assumed.

| Endpoint                    | Success schema                        | Foundation behavior                                                               |
| --------------------------- | ------------------------------------- | --------------------------------------------------------------------------------- |
| GET /api/health             | Health                                | 200 process/config inspection, no dependency ping                                 |
| GET /api/capabilities       | Capabilities                          | 200 actual credential presence, connectivity not_checked; no operations available |
| POST /api/search            | SearchReceipt                         | 400 invalid body; 501 unimplemented                                               |
| GET /api/search/:searchId   | SearchResult                          | 501 unimplemented                                                                 |
| POST /api/quotes/revalidate | RevalidationResponse                  | 400 invalid body; 501 unimplemented                                               |
| POST /api/orders            | Order                                 | 400 invalid body; 501 unimplemented                                               |
| GET /api/orders/:orderId    | Order                                 | 501 unimplemented                                                                 |
| POST /api/payments/checkout | CheckoutResponse                      | 400 invalid body; 501 unimplemented                                               |
| POST /api/webhooks/stripe   | Future verified event acknowledgement | 503 without signing secret; 501 until verification/processing implemented         |

Errors are ApiError: {version:1,error:{code,message,retryable,requestId}}. HTTP mapping: INVALID_REQUEST 400, UNAUTHORIZED/INVALID_SIGNATURE 401, NOT_FOUND 404, CONFLICT/QUOTE_EXPIRED 409, NOT_IMPLEMENTED 501, NOT_CONFIGURED/PROVIDER_UNAVAILABLE 503, INTERNAL_ERROR 500. All responses are no-store and have X-Request-ID. Validation errors never echo request data or secrets.

POST order/checkout contracts require idempotency keys; durable idempotency, authenticated order access, rate limiting, raw Stripe signature verification and replay protection are prerequisites to enabling mutations. No payment success may imply supplier booking or ticket fulfillment. Customer sessions and production authorization are future work; current read/write order operations cannot return success.

Credential presence is inspected locally and returned only as a boolean. Provider connectivity remains not_checked until a real permitted probe succeeds. Database configured is not database reachable. Environment WAYWARD_ENV defaults to development, live must be explicit; invalid values are visible in health and must block future operations. NODE_ENV controls framework optimizations only. No secrets or environment values are sent to clients.

## Additive place lookup (v1)

`GET /api/places?query=Berlin&limit=8&modes=flight,rail`

- query: trimmed string, 2?120 characters, required.
- limit: integer 1?20, default 8.
- modes: optional comma-separated canonical Mode values, at least one if supplied.
  Response `PlaceLookupResponse`: `{version:1, query:string, places:Place[], sources:Array<{id:string,status:"ok"|"unconfigured"|"unavailable"|"unsupported",message:string|null,attribution:string,url:string}>, warnings:string[], fetchedAt:Utc}`.
  Exported schemas/types: PlaceLookupRequestSchema/PlaceLookupRequest, PlaceLookupSourceSchema/PlaceLookupSource, PlaceLookupResponseSchema/PlaceLookupResponse. Existing Place and SearchIntent are unchanged. Pass selected Place objects intact, including opaque providerIds and timeZone. A GeoNames city is not a supplier airport/station ID.
  Source failures are explicit in sources/warnings. All sources unavailable => typed 503 PROVIDER_UNAVAILABLE. Invalid query => 400 INVALID_REQUEST. Empty matches => 200 with empty places. Debounce autocomplete and discard stale responses in frontend. Attribution must remain visible in the consuming UI. Open-Meteo free endpoint is development-only (non-commercial); live use requires a commercial licence/adapter configuration. VBB is regional timetable metadata, not bookable inventory; Duffel requires its own credential. Airport/city records without a known IANA zone are omitted, never assigned a guessed zone. VBB uses its published Europe/Berlin regional zone. No port inventory is invented.
  Sources: https://open-meteo.com/en/docs/geocoding-api ; https://v6.vbb.transport.rest/api.html ; https://duffel.com/docs/api/v2/places/get-place-suggestions .

## Search and repricing increment

SearchReceipt and existing Offer fields are unchanged. SearchResult gains optional `timetableJourneys`, `providerStatuses`, `updatedAt` fields. TimetableJourney is `{itinerary:Itinerary,source:string,attribution:string,price:{kind:"unknown"},availability:"unknown",bookingSupported:false}`. Provider status is `{provider:string,status:"complete"|"failed"|"unconfigured"|"unsupported",message:string|null}`. An empty `offers` array means no supplier offers, never free travel. Frontend can consume timetableJourneys separately but must not offer checkout for them.
POST /api/search now persists pending state, awaits bounded provider requests and persists complete/partial/failed status before returning its receipt. GET reads the persisted result or returns typed 404. Terminal state and warnings describe actual provider outcomes; failed searches never invent offers. Search is synchronous orchestration in this increment, so no unreliable detached background work is used. Development without DATABASE_URL uses atomic .local/wayward files; live deployments and orders require PostgreSQL. Configured database failures never silently fall back. Search IDs are unguessable bearer references; full customer names/email/discount card numbers are not persisted in search records. Formal customer account history is still disabled.
Duffel flight requests use the documented v2 offer request API and six-second supplier search deadline. Credentials and matching response live_mode are required; test offers remain test offers. Money is converted without floating-point arithmetic, local supplier times are converted using place IANA zones, and ambiguous DST times are omitted. Optional bag/airport connection costs remain partial/unknown. No Wayward markup is added. Comfort sorting currently means fewest transfers, not a verified seat comfort score. Regional VBB timetable departure starts at 08:00 local time until a departure-time preference contract is agreed; return searches are explicitly unsupported. Near-stop access/egress remains a missing connection.
POST /api/quotes/revalidate refreshes selected stored Duffel offers, persists the quote, detects price/timing changes and refuses expired/unknown expiry. Timetable IDs and unknown offer IDs return 404. This does not reserve seats or issue tickets. Multi-offer quotes are not assumed to be compatible or jointly bookable; order validation will enforce compatibility and complete totals separately.
Provider docs: https://duffel.com/docs/api/v2/offer-requests/create-offer-request ; https://duffel.com/docs/api/offers ; https://v6.vbb.transport.rest/api.html .

## Durable draft orders and Stripe verification increment

CreateOrderRequest adds optional `acceptChanges:boolean`; set true only after showing the refreshed price, conditions and timings to the customer. Order response remains unchanged. POST /api/orders atomically creates a **draft**, with payment/settlement/fulfillment not_started and no supplier booking ID or tickets. No booking is performed. Requirements: PostgreSQL configured/reachable, an existing revalidated quote in that same database, nonexpired complete supplier price in matching live/test environment, verified itinerary compatibility, matching passengers, explicit acceptance of quote changes. Multi-offer/multi-supplier ordering remains typed 501. Unknown/partial/indicative prices are never orderable.
An opaque HttpOnly SameSite=Strict cookie (`wayward_session`, Path=/api; Secure in live mode) protects order retrieval and checkout. Browser same-origin fetch sends it automatically. Do not expose it to JavaScript or store it in localStorage. There is no full account system yet; clearing this cookie loses order access, so this is a development guest-session boundary, not a production account recovery design. Different sessions receive 404 for another session's order. Missing sessions receive typed 401. Cross-origin browser order operations are rejected. APP_URL must be configured for live sessions. Order idempotency is session-scoped; reusing a key with a different request gives 409. Quote consumption, creation and retry handling are serialized with PostgreSQL row/advisory transaction locks.
PostgreSQL initialization creates only the `wayward_private` schema and `wayward_private.records` table, enables RLS, and does not expose tables in Supabase's public Data API schema. Use an owner/service database role (server only). Existing local development search files are not silently imported: re-search/revalidate after configuring DATABASE_URL. There is no memory/file fallback for orders or payments.
GET /api/health/dependencies returns DependencyHealth: `{version:1,database:{configured:boolean,connectivity:"not_checked"|"verified"|"failed"},searchStorage:"postgresql"|"development_file"|"unconfigured",stripe:{credentialsPresent:boolean,webhookSecretPresent:boolean,connectivity:"not_checked",checkoutEnabled:false}}`. Database verification is a real SELECT 1 probe; Stripe key presence is not connectivity. Existing Health and Capabilities schemas remain compatible.
Stripe SDK integration validates test-mode keys in development, builds manual-capture Checkout parameters, and verifies webhook signatures against bounded raw bodies with a five-minute timestamp tolerance. Webhook replies use StripeWebhookResponse `{version:1,received:true,duplicate:boolean,ignored:boolean}`. Valid supported PaymentIntent events require durable order/payment mapping, matching amount/currency/environment and a current Stripe retrieval; event IDs are deduplicated transactionally to prevent replay effects. Supported subscriptions: payment_intent.amount_capturable_updated, payment_intent.succeeded, payment_intent.payment_failed, payment_intent.canceled. Other signed events are ignored explicitly. Amount mismatch/unmapped events are rejected, not acknowledged as successful fulfillment. Unknown payment statuses fail closed. Authorization, capture, supplier settlement and ticket fulfillment remain distinct; a payment event never writes ticket documents or confirms a supplier booking.
**Checkout remains disabled** with typed 501 after configuration/order authorization checks until supplier booking, full passenger identity collection, settlement and compensation are implemented. No Stripe session is created and no funds are authorized or captured by the current route. The pure parameter builder is preparation, not a completed checkout integration. Missing database/Stripe/webhook keys produce typed 503, never fabricated success. Webhook signature failures produce 401. Account recovery, supplier booking, settlement, fulfillment and aftersales operations remain unfinished.
